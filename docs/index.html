User guide

Write HTTP API tests as plain text, then run them.

SnapAPI is a Python HTTP testing DSL. You author .sapi files with GET, POST, EXPECT, and SAVE, then run snapapi file.sapi. No YAML maze, no generated client. The older .snaptest extension still works.

Try it in the browser Write your first suite

Readable DSL

Suite, test, request, body, expects. Indentation is cosmetic. Comments are // lines. Modern GET: aliases and legacy REQUEST: both parse.

Checks that match real APIs

Status, body contains, JSONPath, headers, schema, XPath, duration, and OpenAPI contract checks — plus SAVE into ${var}.

Built for CI

JUnit, HTML, and JSON reports, VCR cassettes, --safe-url, tag filters, retries, and a Python helper to run suites from your own code.

In-browser playground

Type a .sapi suite and click Run. A client-side interpreter hits an in-memory mock so you do not need Python or a network.

Why SnapAPI?

SnapAPI is for HTTP tests that should read like the API. The file is the request.

You write a suite of named tests. Each test has one or more HTTP steps, then EXPECT and SAVE. A reviewer sees the path, the body, and the checks in the same file you run.

The test looks like the API

A reviewer sees POST: /users, EXPECT: json $.email, SAVE: id FROM $.id. The contract and the test are the same text.

HTTP primitives as keywords

Chaining, WAIT, EXAMPLES, VCR, redacted fail dumps, curl/HAR on fail, profiles, and OpenAPI checks are keywords in the suite.

Plain text in git

.sapi files are text. They diff, review, and branch with the rest of the repo.

Shared by the people who own the API

SDETs and backend reviewers can write and review the same files. The suite is the contract.

When it fits

  • The test is the HTTP call
  • You want smoke and regression that reviews as the contract
  • QA and backend share the same files
  • You want to run those files from the CLI, or from Python with run_suites

Thirty-second example

SUITE: Book Store
DESC: Validates the user API
URL: https://api.example.com
HEADER Content-Type: application/json

TEST: Create User
  POST: /users
  AUTH: bearer ${TOKEN}
  BODY: {"name": "Jane", "email": "jane@example.com"}
  EXPECT: status == 201
  SAVE: userId FROM $.id

TEST: Get User
SETUP: Create User
  GET: /users/${userId}
  EXPECT: status == 200
  EXPECT: json $.email == "jane@example.com"

On your machine that file is executed by the snapapi CLI. In this guide, the playground runs the same shape of suite against a built-in mock at /api/users.

What SnapAPI is not

There is no language server, gRPC, or WebSocket support. OpenAPI smoke generation and contract checks exist; they do not replace a full spec toolchain. The playground implements a useful subset of the DSL — FILE, GRAPHQL, IMPORT, oauth2, schema, and XPath still need the Python CLI.
